# BUFR Tanks

GEODE can ingest NCEP BUFR tanks, the daily files laid out as
`{root_path}/YYYYMMDD/bAAA/xxBBB`, where `AAA` is the BUFR data category and `BBB`
is the local subcategory.

Tanks are ingested with `geode ingest bufr_tank_reader`. See
[Command Line](command-line.md#ingest-bufr-tanks) for usage and
[Getting Started](getting-started.md#bufr-tanks) for configuration.

## From tank to dataset

Three sets of files decide how a tank is stored:

| File | Purpose |
|---|---|
| `configs/bufr/table_a_mapping.yaml` | Maps each tank to a dataset name, format, and restricted flag |
| `tank/config/bAAA_xxBBB.yaml` in SPOC (`src/spoc`) | The `bufr-query` mapping that decodes the tank |
| `configs/bufr/dataset_splits.yaml` | Optional grouping of a dataset's observations by the value of a variable |
| `configs/bufr/satellite_names.yaml` | Names for datasets split by satellite |

Many tanks can share one dataset. Datasets may also be stored under a longer name:

- Satellite tanks are split by satellite, stored as `<dataset>_<name>`, for example
  `radiance_atms_npp`. Names come from `configs/bufr/satellite_names.yaml`, keyed by WMO
  Common Code Table C-5 satellite ID. A satellite that is not listed keeps its number, for
  example `radiance_atms_227`. Datasets that already name their satellite, such as
  `marine_altimeter_jason3`, are not split.
- Datasets listed in `dataset_splits.yaml` are stored as `<dataset>_<group>`. GNSS-RO
  uses this to split by mission, for example `gnssro_bending_angle_spire`. An ID that is
  not listed goes to a group named `other`, so no observations are lost.

Restricted tanks are refused unless `bufr_tank.include_restricted` is set.

## How repeated data is stored

GEODE appends new data along the `Location` dimension, so any other dimension must keep
the same size from file to file. BUFR sequences that repeat a variable number of times
would break that, so each repeated sequence in a tank is stored in one of these ways:

| Sequence | Stored as |
|---|---|
| One vertical or long variable-length sequence | One row per element, using `group_by_variable`. Rows with no values are removed |
| Channels, and fixed sequences of 20 or more elements | A dimension |
| A fixed sequence nested inside a fixed sequence | One dimension per parent element, such as `Avhrchn1` to `Avhrchn7` |
| Short lists, such as cloud layers | Numbered variables, such as `cloudAmount1`, `cloudAmount2` |
| Single-value sequences, such as receipt time and bulletin | The first element |
| Raw report text, for tanks without levels | Joined into `MetaData/rawReport` |
| Raw report text, for tanks with levels | Not stored |
| Source file names | Not stored |

Numbered variables use the fixed count from the BUFR table when there is one. Otherwise
the limit comes from SPOC's `tank/aux/bufr_tank_sequence_sizes.yaml`, which is based on sample
data, and any elements beyond the limit are not stored.

Other details worth knowing:

- Strings are stored as variable length, because their decoded width depends on the
  longest value in each file.
- 64-bit integer variables are stored as floats, so that missing values stay missing.

### Tanks with several mappings

`group_by_variable` can only flatten one sequence per mapping. A tank with several
unrelated sequences has one mapping per sequence, named `bAAA_xxBBB_<profile>.yaml`:

- `b003/xx010` (GNSS-RO) has three profiles on different vertical grids. Each is stored
  as its own dataset: `gnssro_bending_angle`, `gnssro_refractivity`, and
  `gnssro_retrieval`.
- `b001/xx103` (moored buoys) has its records stacked as rows of one dataset. The
  `MetaData/recordType` variable says whether a row is `surface`, `temperature_salinity`,
  `currents`, or `wave_spectra`. Variables that do not apply to a row are missing.

## Tanks that share a dataset

The store refuses an append whose variables differ from what is already stored, because
the variables that were not written would stop growing and rows would no longer line up.

So every tank in a dataset gets the same variables. A variable that a tank does not have
is mapped to a mnemonic no subset contains, `ABSENT`, which reads as all missing. These
are labelled with a comment in the YAML.

## Adding or regenerating mappings

Mappings are generated by `dev/ush/generate_bufr_tank_yamls.py`. To add a tank:

1. Add it to `configs/bufr/table_a_mapping.yaml`.
2. Produce the generator's inputs for every tank, inside the GEODE container:

    ```bash
    show_queries.x <tank_root>/bAAA/xxBBB > queries/bAAA_xxBBB.txt
    gettab <tank_root>/bAAA/xxBBB > tables/bAAA_xxBBB.txt
    ```

3. Run the generator from the repository root. It needs the `spoc` submodule, whose
   curated configs supply many variable names:

    ```bash
    python dev/ush/generate_bufr_tank_yamls.py queries tables . src/spoc/tank/config
    ```

The generator reports tanks it could not map, and `problems` it found when giving tanks
in a dataset the same variables. Include every tank in the dataset when you run it, since
adding a tank can change the shared variable list for the others.

Mnemonics starting with `.` are left out, with a comment in the YAML, because
`bufr-query` cannot parse them yet.
